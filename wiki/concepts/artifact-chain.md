# Artifact Chain

> 각 작업 단계가 **버전 관리에 커밋된 파일**로 끝나고 다음 단계가 그것을 읽으며 시작하는 패턴. 단계 간 인터페이스가 회의와 핸드오프가 아니라 파일이 되면, 커밋 체인 자체가 audit trail이 되고 커밋 이벤트가 다음 단계의 트리거가 된다.

## Overview

전통적인 프로세스에서 단계 사이를 잇는 것은 문서, 티켓, 사인오프다. 각 핸드오프에서 소유권이 이전되고 의미가 조금씩 샌다 — 엔지니어링에 도달할 때쯤이면 발안자가 의도한 것에서 여러 단계 떨어져 있다.

artifact chain은 이 인터페이스를 **커밋된 파일 하나**로 고정한다. 세 가지가 동시에 따라온다:

1. **핸드오프가 결정론적이 된다.** 다음 단계의 입력이 정확히 무엇인지 파일 경로로 지정된다.
2. **트리거가 생긴다.** 커밋·머지 이벤트에 자동화를 걸 수 있다. 승인된 `intent.md`가 design pass를 발사하고, 승인된 `spec.md`가 plan mode를 발사한다.
3. **audit trail이 공짜로 나온다.** 누가 무엇을 요청했고, 에이전트가 무엇을 만들었고, 누가 승인했는지가 git history에 이미 있다. 별도 추적 시스템을 세울 필요가 없다.

에이전트 맥락에서 특히 중요한 이유는 **에이전트가 상태를 갖지 않기 때문**이다. 비대화형으로 도는 세션은 이전 세션의 대화를 기억하지 못한다. 커밋된 아티팩트는 세션 사이에 살아남는 유일한 기억이다. 대화가 아니라 파일이 프로세스를 잇는다.

## 체인의 형태

[[ai-native-sdlc]]에서 체인은 이렇게 흐른다:

```
intent.md  →  spec.md  →  plan.md  →  diff + tests  →  PR + review findings  →  incident record
   ↑                                                                                    │
   └────────────────────────────────────────────────────────────────────────────────────┘
                        control band breach가 다음 intent.md를 쓴다
```

| 아티팩트 | 누가 쓰나 | 누가 승인하나 | 무엇을 트리거하나 |
|---|---|---|---|
| `intent.md` | 발안자 + 에이전트 (또는 모니터링 에이전트) | product owner | 요구사항·설계 pass |
| `spec.md` | 에이전트 (조직 skill을 제약으로) | product owner, 고위험은 tech lead | plan mode |
| `plan.md` | 에이전트 (plan mode) | 엔지니어, 고위험은 아키텍트 | 구현 |
| diff + tests | 에이전트 | — | PR |
| PR + findings | 에이전트 리뷰 pass | code owner (branch protection) | 파이프라인 |
| incident record | 모니터링 에이전트 | 서비스 오너 triage | 새 `intent.md` |

체인이 닫혀 있다는 점이 핵심이다. 마지막 고리가 첫 고리로 되돌아가므로 선형 프로세스가 아니라 루프다.

## 왜 마크다운인가

초기 단계에서 `.md`가 지배적인 이유는 포맷 취향이 아니다. **product owner와 에이전트가 같은 파일을 읽고 그것에 따라 행동할 수 있기 때문**이다. 사람이 읽을 수 있고(human readable) 기계가 실행할 수 있다(machine actionable).

이것이 만드는 실질적 차이: 엔지니어가 아닌 사람이 프로세스의 첫 단계를 직접 소유할 수 있다. git 경험이 없어도 버전 관리 시스템 커넥터를 통해 에이전트가 대신 커밋한다.

Build 이후로는 아티팩트가 코드와 그 기록(테스트, PR, 체크 실행 결과)으로 바뀐다. 마크다운은 **사람의 판단이 아직 주된 산출물인 구간**의 포맷이다.

## 좋은 아티팩트의 조건

플레이북이 제시하는 각 아티팩트의 합격 기준에는 공통점이 있다 — **다음 단계가 대화 없이 소비할 수 있는가.**

- `intent.md`: 무엇을 원하고, 왜, 어떤 제약 아래인가. 형식 언어 불필요. Open questions를 명시적으로 남긴다.
- `spec.md`: 만족시킬 수 없는 **상충 정책을 명확히 기술**해야 한다. 플래그된 우려는 엔지니어링이 보기 전에 정책 소유자와 해소된다.
- `plan.md`: *"대화를 본 적 없는 엔지니어가 계획만 보고 구현할 수 있을 때까지"* 반복한다. 바뀌는 파일, 작업 순서, 위험, 증명 방법을 명시.
- PR: 기계적 증거(테스트 출력, 빌드 로그, 스크린샷 diff)가 이미 첨부되어 있어야 리뷰어가 intent와 risk에 집중할 수 있다.

`plan.md`의 기준이 특히 시사적이다. "에이전트가 이해할 수 있는가"가 아니라 **"제3의 사람이 이해할 수 있는가"**가 기준이다. 아티팩트는 에이전트를 위한 것이 아니라 프로세스를 위한 것이다.

## 동기화 문제

체인의 가장 약한 지점은 **아티팩트가 현실과 어긋나는 것**이다. 구현이 계획에서 벗어났는데 `plan.md`가 그대로면 그 파일은 audit trail이 아니라 거짓말이 된다.

플레이북의 처방:
- 구현이 계획에서 벗어나면 **같은 커밋에서** `plan.md`를 갱신한다. hook으로 이 동기화를 강제하는 것을 고려한다.
- PR 리뷰가 실제 diff를 커밋된 `plan.md`와 대조한다 (compliance pass).
- 측정 지표로 **"머지된 diff가 커밋된 `plan.md`와 여전히 일치하는 빈도"**를 lagging indicator로 추적한다.

즉 동기화는 규율이 아니라 **자동화된 검사**로 유지된다. 이것이 없으면 artifact chain은 문서화 부채로 퇴화한다.

## 레거시 시스템과의 공존

조직에는 이미 아티팩트를 추적하는 시스템이 있다 — Jira의 work item, 규제 추적성을 갖춘 요구사항 도구, Figma의 디자인, change board의 승인. 감사인이 이미 수용하고 다른 팀이 의존하므로 밀어내기 어렵다.

규칙: **아티팩트마다 하나의 시스템만 source of truth로 지명하고, 나머지는 사본이나 링크를 갖는다.** 지명이 아티팩트별로 달라도 된다.

- **repo 중심** — 마크다운이 권위 있고 레거시가 커밋 내 파일을 참조. 한 도구, 한 timestamp authority.
- **레거시 중심** — Jira/ServiceNow가 권위 있고 마크다운은 작업 사본. Claude가 세션 시작에 기록을 읽고 MCP로 결과를 되쓴다.
- **linkage** — 아티팩트는 record ID를, 레거시 record는 commit SHA를 갖는다. source of truth가 둘이라는 것을 받아들이는 전환기 출발점.

두 시스템이 공존해도 된다. **링크가 있거나 한쪽이 source of truth로 선언되어 있기만 하면.**

## Key Points

- 단계 간 인터페이스를 **커밋된 파일**로 고정하면 핸드오프·트리거·audit trail이 한꺼번에 해결된다.
- 에이전트는 stateless다. 커밋된 아티팩트가 세션 사이에 살아남는 유일한 기억이다.
- 마크다운은 **사람과 에이전트가 같은 파일을 읽을 수 있는 구간**의 포맷이다. Build 이후로는 코드와 그 기록이 아티팩트가 된다.
- 아티팩트의 합격 기준은 "다음 단계가 대화 없이 소비할 수 있는가"다.
- **동기화는 규율이 아니라 자동화된 검사로 유지된다.** hook과 리뷰 pass가 없으면 문서화 부채로 퇴화한다.
- 레거시를 대체하지 않는다. 아티팩트마다 source of truth를 하나 지명하고 나머지는 링크한다.

## Open Questions

- 체인이 길어질수록 각 단계의 리뷰 부담이 쌓인다. 작은 변경에 대해 `intent.md`→`spec.md`→`plan.md`를 전부 거치는 것은 과잉 아닌가? 플레이북은 단계 생략 기준을 제시하지 않는다.
- 아티팩트와 코드의 동기화 검사를 어디까지 자동화할 수 있나? "diff가 `plan.md`와 일치하는가"는 결국 모델의 판단이므로 결정론적이지 않다.
